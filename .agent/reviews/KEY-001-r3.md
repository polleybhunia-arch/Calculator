## Assessments
- **Requirement satisfaction**: All eight ACs are met by the shipped code. I verified AC-6/AC-7's
  focus/native-activation behavior myself across digit, operator, action and equals buttons, for
  `Enter` and `Space`, for single presses, held keys, repeat-first events and focus changes mid-hold.
  The four-line fix is minimal, sits inside the existing branch, changes no other path, and the
  comment explains *why* (`D-012` rejected, r2 F-1) rather than *what* — matching CLAUDE.md §4.
- **Test adequacy / false confidence**: Generally strong and unusually self-aware — whole-pair display
  equality, preconditions asserted before "cleared" states so `0` cannot pass by coincidence, and a
  `spyOnDispatches` oracle where the display is provably blind. 11 of 13 valid mutants died. The two
  survivors are the false-confidence signal: the suite's green is being read as "the fix is general",
  but it only demonstrates "the fix works for `Enter` on a digit button". Both gaps are one test each.
- **Edge cases missing**: held `Space` on a focused button (F-1); held `Enter`/`Space` on a focused
  non-digit button with a dispatch-count oracle (F-2). Everything else I could construct in this area
  is either covered or provably inert (table above). Held `Escape`/`Delete` remains undefined by OQ-4
  and is idempotent — correctly documented as "Not covered" in the matrix, no action.
- **Regression risk**: Low for existing behavior. The GUARD row replays all eight README click
  sequences with the keydown listener and `blur()` installed; the 20 `dom-click` rows and both
  divide-by-zero suites are unmodified and green; `index.html` and `style.css` are untouched; no
  pre-existing test was weakened, skipped or deleted (`validate.mjs state` = OK, and the three
  modified test files are covered by `D-008`/`D-009`). The real regression risk is *future*: the two
  unpinned guarantees (F-1, F-2) are in the exact four lines that have now produced two escaped
  defects, and a plausible future simplification (`allowsRepeat`-gating, or "digits repeat anyway")
  would reintroduce a user-visible bug with a green suite.
- **Conventions & complexity**: 2-space indent, single quotes, semicolons, `const`/`let`, `camelCase`,
  `UPPER_SNAKE` for `KEY_MAP`/`OPERATORS`; classic scripts, no modules, no build step, zero
  dependencies; `node:test` + `node:assert/strict`; behavior-stating test names; branch
  `agent/KEY-001-keyboard-input`, `KEY-001: …` commit subjects, nothing pushed. `KEY_MAP` is derived
  from `NUMBER_CHARACTERS` and `OPERATORS` rather than hand-copied, which closes carried-forward
  item 4 properly. One dead-simple redundancy: the guard's `return` is immediately followed by the
  branch's own `return` (`script.js:100` and `:102`) — correct, readable, not worth changing.
- **Security implications**: `mapKey` is a closed `Map`-based allowlist; `constructor`/`__proto__`
  cannot resolve through it or through `isInput`, which I confirmed by clicking and holding `Enter`
  on synthetic buttons carrying those `data-*` values (no throw, no state change, `markupWrites`
  empty). Display writes go through `textContent` only. `preventDefault()` is still bounded: mapped
  modifier-free keys, plus the one new repeat-on-focused-button case (F-3) — `Ctrl+R`, `Cmd+/`,
  `Tab`, `F5`, `a`, `ArrowLeft` and a single `Space` all stay untouched, pinned by tests. No new
  dependency, no network, no storage, no `eval`/`new Function`/`innerHTML`. The formal security
  verdict is `security-reviewer`'s, not mine.
- **Performance implications**: No material risk. The hot path is one `keydown` listener doing two
  string comparisons, an `Object` destructure and one `Map.get` — O(1) per event, independent of
  state size. The new guard *reduces* work on held keys (early return before `mapKey`). `history`
  is the only growing structure and it is bounded by user typing and reset on `=`/`AC`. Examined:
  the keydown path, the click path, `render()`'s `history.join('')`, and the stub's bubble loop
  (test-only). No measurement needed at this scale.
- **Architecture fit**: The DOM/core split holds — the key map and repeat policy are pure and in
  `calculator-core.js`, `script.js` keeps one dispatch seam for both channels and synthesizes no
  `button.click()`. The one wrinkle is conceptual, already recorded in the code comment: two
  independent repeat policies now exist (`allowsRepeat` for the document channel, an unconditional
  suppression for the native-activation channel). That is the correct answer — `D-012`'s
  `allowsRepeat`-gated version demonstrably would not have fixed the digit case — but it is exactly
  why F-2's test matters: nothing but a comment currently stops the two policies being "unified".
