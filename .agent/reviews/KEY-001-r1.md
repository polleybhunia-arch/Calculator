Everything else — the map, the modifier policy, `preventDefault` discipline, the repeat policy, key-vs-click parity including the `CALC-001` mid-chain divide-by-zero case, and the README — holds under independent execution.
- **Test adequacy / false confidence**: generally strong: preconditions are asserted before "cleared" states (so `0` cannot pass by coincidence), whole-pair display equality is used everywhere, the two call-count spies are necessary rather than decorative (M2 proves it), and expected values are reused from BOOT-001/CALC-001 oracles rather than recomputed from the code under test. The false-confidence spot is precisely F-1: a row whose *name* asserts the blur behavior while its *mechanics* cannot observe it, plus F-3 where three rows are believed to guard the `Enter`/`Space` branch and only one does. No `.only`/`.skip`, no deleted or weakened pre-existing tests (`git diff --name-status` on `tests/` shows `M` only for `dom-stub.js`, `source-scan.js`, `source-safety.test.js`, each covered by a decision record; the six untouchable files are byte-identical).
- **Edge cases missing**: held `Enter`/`Space` on a Tab-focused button (native repeat activation bypasses `allowsRepeat`; currently masked by the unconditional blur — see F-2); `Alt`-held mapped key at page level (F-6); a mapped key pressed while a calculator button is focused (works — `Tab` to `7`, press `5`, one action — but unpinned); `Escape`/`Delete` auto-repeat is deliberately undefined by AC-7/OQ-4 and is harmless because `clear` is idempotent (the matrix flags this honestly).
- **Regression risk**: low and well covered. The shared click handler gained `blur()`, which every pre-existing click test runs through; the GUARD row plus the 20 `dom-click` rows and the divide-by-zero suites are green, and I re-derived the GUARD "before" state independently (9/9). The `inputFromElement` rewrite from three hand-kept tables to `isInput` is behavior-identical (`isNumberValue` ≡ `length === 1 && NUMBER_CHARACTERS.includes`, `OPERATORS.has` ≡ `OPERATOR_VALUES.includes`, `ACTIONS.has` ≡ `ACTION_VALUES.includes`, and `Map.has` is immune to `constructor`/`__proto__`), and M3/M7 prove the filters are now pinned — closing carried-forward item 1 for real.
- **Conventions & complexity**: conforms to CLAUDE.md §4 — 2-space indent, single quotes, semicolons, `const`/`let`, `camelCase`, `UPPER_SNAKE` (`KEY_MAP`), behavioral test names, comments that explain *why*. No dependencies, no build step, classic scripts only (`index.html` correctly unchanged). `D-005` holds in the diff: one `dispatch(input)` seam (the keydown path calls it, never `button.click()`), the repeat policy is a pure core function, the vocabulary is exported once and `script.js` no longer hand-lists digit/operator/action values (carried-forward item 4 closed), and the core still touches no DOM API. Complexity is proportionate; `KEY_MAP` deriving its digit and operator entries from `NUMBER_CHARACTERS`/`OPERATORS` is the right call — it is what makes the "every mapped descriptor is accepted by `isInput`" row non-trivial.
- **Security implications**: the key map is a closed `Map` allowlist returning a fresh copy, so no caller can mutate shared entries; nothing input-derived reaches `innerHTML`/`eval`/`new Function` (display writes stay `textContent`); `preventDefault()` is called only for mapped, modifier-free keys, so `Ctrl`/`Meta`/`Alt` shortcuts and `Tab` navigation survive (RK-5 addressed and pinned by M5/M6). Residual: the widened static scan has two real blind spots (F-4, F-5), and the `document`-level `keydown` listener would hijack typing if the page ever gained a text input — worth a comment if a future unit adds one. Carried-forward item 5 (`CALC_STUB_TRANSFORM` unrecorded in gate evidence) is acceptable to leave open in my judgment, with one caveat worth recording: it is not silent — the stub emits a `CALC_STUB_TRANSFORM active` process warning, `run-gate.mjs` appends stderr after stdout and keeps the last 40 lines, so a mutated run leaves that warning inside `outputTail` (I confirmed the four recorded final evidence files contain no such warning). That is a detectable, not a proven-absent, guarantee; hardening `run-gate.mjs` remains human-owned.
- **Performance implications**: no material risk. Per keystroke the handler does one `Map.get`, one object spread of a two-field descriptor, and one re-render writing two `textContent` values — O(1), no allocation in a loop, no repeated DOM queries (the three element handles are captured once at load). `KEY_MAP` is built once at script load (~25 entries). `blur()` per click is O(1). Examined: the keydown path, `dispatch`/`updateDisplay`, and `KEY_MAP` construction; nothing grows with input length except `history`, which is unchanged by this unit.
- **Architecture fit**: clean. The keyboard channel is an adapter-level translation onto an existing seam; the only DOM-specific knowledge in `script.js` is `event.target`, focus and `preventDefault`, exactly the line `D-005` clause 6 draws. `isCalculatorButton` reading `dataset` without validating values is correct for its purpose (native activation must be skipped even for a malformed button) and is documented as such.
