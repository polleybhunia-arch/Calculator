# KEY-002 — On-screen press feedback for keyboard input

## Objective
When a mapped key is pressed, the matching on-screen button briefly highlights, so the user
sees which calculator button their keystroke hit. Purely presentational: no change to
calculator state or display text.

## Context
Requirement R-12 in `.agent/plan.md`, raised as a usability idea in handoff PLAN-01. It is
**contingent on OQ-5**: if the user does not want press feedback, this unit is dropped rather
than implemented. Buttons already have a `:active` mouse style in `style.css`; keyboard
presses currently produce no visual response, so a keyboard user gets display feedback only.

Behavior is bound through `data-*` attributes, not class names (CLAUDE.md §4), so the button
lookup uses the existing `data-number` / `data-operator` / `data-action` attributes that the
KEY-001 key map already produces.

## Dependencies
- `KEY-001` — supplies the key map and the `keydown` listener this unit decorates; without it
  there is no keyboard event to react to.

## Acceptance Criteria
- AC-1: Given the loaded page, when `7` is pressed (`keydown`), then the button carrying
  `data-number="7"` gains the press-feedback class and no other button does; and when the key
  is released (`keyup`), then that class is removed again.
- AC-2: Given the loaded page, when an unmapped key or a modifier combo (per KEY-001 AC-5) is
  pressed, then no button gains the press-feedback class.
- AC-3: Given any keyboard sequence with feedback active, when the sequence completes, then both
  display lines and the calculator state are exactly what KEY-001's tests expect for that
  sequence (feedback is side-effect free); and after a `keyup` with no preceding mapped
  `keydown`, no button is left highlighted.
- AC-4: Given `style.css`, when the feedback class is applied, then it is a `kebab-case` class
  with the same visual affordance family as the existing `.btn:active` rule, and the responsive
  rules at `max-width: 360px` are unaffected.

## Required Tests
- **Unit**: none expected (no pure logic added beyond a selector lookup); if a pure
  "input descriptor → button selector" helper is introduced, it gets
  `tests/unit/button-lookup.test.js` covering every input type and an unmapped input → `null`.
- **Integration** (`tests/integration/key-feedback.test.js`): AC-1…AC-3 through the DOM stub —
  class added on `keydown`, removed on `keyup`, never added for unmapped/modifier keys, never
  left stuck after an interleaved sequence (`keydown 7`, `keydown 8`, `keyup 7`, `keyup 8`).
- **Regression**: expand `tests/regression/keyboard-and-click-parity.test.js` with one test
  proving displays are byte-identical with feedback enabled; register in
  `tests/regression/REGISTRY.md` with origin `KEY-002`.
- **Manual (UNVERIFIED without a browser)**: the highlight is actually visible and its duration
  feels right — recorded as a user check, never as PASS (D-001 residual risk, CLAUDE.md §16).

## Relevant Files / Components
- `script.js` — `keydown`/`keyup` handlers toggling the class on the matching button
- `style.css` — the press-feedback class
- `calculator-core.js` — only if an input-descriptor → selector helper belongs there
- `tests/integration/key-feedback.test.js`, `tests/helpers/dom-stub.js` (class list support)
- `README.md` — one line under Features if the feedback is user-visible behavior

- `security_review`: expected `N/A: presentation-only change, no new input surface` — the
  orchestrator confirms, since KEY-001 already covered the input path.
- `docs`: `UPDATED` or `N/A: <reason>` depending on whether the feedback is described in README.
- No KEY-001 or BOOT-001 test modified (any change needs a `kind: test-change` decision record).

## Risks / Open Questions
- **OQ-5 (owner: user, BLOCKS READY)**: is press feedback wanted at all, and is a ~120 ms
  highlight acceptable? If "no", this unit is cancelled, not implemented.
- Risk (owner: implementer): a stuck highlight if `keyup` is missed (window blur, key held
  during an alert). Mitigation: AC-3 interleaving test; consider clearing all highlights on
  `window` blur — an implementation detail, not a new AC.
- Risk (owner: user): timing/appearance cannot be verified in Node; residual risk accepted or
  the unit stays `UNVERIFIED` on that point.
