## Notation (extends `BOOT-001.matrix.md` / `CALC-001.matrix.md` "Notation")

- **Click sequence**: as before — digits/`.`/operators/`=`/`AC`/`DEL` tokens, one `click` per token via `page.press(...)` or `page.click(page.buttonFor(...))`.
- **Key sequence**: space-separated `event.key` tokens applied as synthetic `keydown` events, in order, to a fresh page. A bare token (`4`, `+`, `Enter`, `Backspace`, `Escape`, `Delete`, `x`, `X`, `,`) carries no modifier and `repeat: false`, and is dispatched on `document.body` unless a row says a button is focused. `Ctrl+r` / `Cmd+/` / `Shift+=` etc. mean a `keydown` with that named modifier flag (`ctrlKey`/`metaKey`/`shiftKey`) true and `key` set to the literal value named (per AC-5, the browser — not the mapper — turns a physical `Shift+8` into `event.key === '*'`, so the test dispatches `key: '*'` with `shiftKey: true`, it never dispatches `key: '8'` with a modifier and expects the mapper to translate it).
- **E** / **C** / glyphs / "fresh state" / "fresh page": unchanged from `BOOT-001.matrix.md`.
- `mapKey(key, modifiers)` and the auto-repeat policy are referred to by role, not by a fixed name: `calculator-core.js` will export a pure key-mapping function and a pure repeat-policy function (D-005 clauses 5–6); the exact names are the implementer's choice, the way the input-descriptor shape was the implementer's choice before `D-003` recorded it. Row text says "the key map" / "the repeat policy" rather than a literal identifier.

## Why `dom-stub.js` must change, and a third decision record is needed (flagged, not decided here)

The dispatch names two existing files the orchestrator will cover with a `kind: test-change` decision (`tests/helpers/source-scan.js`, `tests/regression/source-safety.test.js`). Extending `tests/helpers/dom-stub.js` is not optional: AC-6's fix adds `element.blur()` to the shared mouse-click handler in `script.js`, which runs for **every** existing click-path test (all 20 `dom-click.test.js` rows, all 8 `readme-behavior.test.js` rows, all of `divide-by-zero-click.test.js` and `divide-by-zero.test.js`) — if `Element` has no `blur` method, every one of those tests throws the moment the fixed `script.js` runs through the stub, not just the new KEY-001 rows. AC-6 and AC-7 are also otherwise untestable without `document.activeElement`, `focus()`/`blur()`, and a simulated native `Enter`/`Space` activation (the dispatch's own stub-fidelity paragraph names these). `git diff --name-status` will therefore show `M tests/helpers/dom-stub.js`, which `validate.mjs`'s `checkTestChanges` (any `M`/`D` under `tests/`, not only `*.test.js`) flags exactly like the other two files. **This needs its own `kind: test-change` decision record** (old behavior: no focus/blur/activeElement modeling; new: adds it, changes nothing about parsing/click/bubbling) — the dispatch only pre-authorized two files' decisions; this is a third one for the orchestrator to add, not something this design can resolve by itself.

Required new `dom-stub.js` primitives (extends `BOOT-001.matrix.md` "Stub fidelity requirements", which already anticipated `document.addEventListener`):
7. `document.activeElement` tracks the most recently focused element; `null` on a fresh page load (nothing is focused until a click or an explicit `focus()`).
8. `element.focus()` sets `document.activeElement` to that element and clears it from whatever element held it before (at most one focused element, matching a real DOM) — models "reached by Tab" when called directly, with no click.
9. `element.blur()`, called on the currently focused element, clears `document.activeElement` back to `null` — models the AC-6 fix.
10. `page.click(target)` performs the browser's own default behavior of focusing the clicked element (`target.focus()`) **before** dispatching the `click` event, so a later `element.blur()` inside the click handler has an observable effect (otherwise blur-after-click would be blurring nothing).
11. Native default action for `Enter` / `Space`: when a `keydown` with `key === 'Enter'` or `key === ' '` bubbles from `document.activeElement` (a `<button>`) through the tree and is **not** `defaultPrevented` by any listener that ran during the bubble, the stub performs a `click()` on that button once the bubble phase completes — suppressible by `preventDefault()`, exactly like a real browser's default action.
12. No further stub change is needed to count `preventDefault()` invocations: `dispatch(type, target, init)` already merges `init` into the event object, so a row can pass its own counting `preventDefault` function in `init` (a test-file-local technique, not a stub change).

Anything the stub still cannot model (real focus rings, real OS auto-repeat timing, a real browser's exact default-action semantics for every element type) stays `UNVERIFIED` — see "Not covered".

## Not covered (with reason)

- **Numpad key values as a separate mapping branch**: `event.key` normalizes a numpad digit/`.`/operator/Enter to the identical string as its top-row counterpart (this is the stated reason the unit's Context chose `event.key` over `event.code`), so no separate row exists for `"Numpad5"`-style literal values — they never occur in a real `KeyboardEvent.key`. Documented in the relevant unit-row notes above rather than as a silent gap.
- **Auto-repeat policy for the clear action** (`Escape`/`Delete`): AC-7 and OQ-4 state a policy only for digits/`.`/`,`/`Backspace` (repeat) and Enter/`=`/operators (no repeat); neither says what a held `Escape`/`Delete` should do. `clear` is idempotent regardless of how many times it is applied, so no test can discriminate one choice from the other — not blocking, but flagged for the planner/orchestrator as an unresolved (harmless) gap in the AC/OQ text.
- **`data-*` attribute precedence with several attributes on one synthetic element** (a fuller version of sec1 F-3's suggestion): the dispatch's item 1 asks only for "no state change and no exception" on out-of-range values, not a precedence probe; adding one would be scope creep beyond the carried-forward instruction.
- **Non-US keyboard layouts** where a physical `x` key might not produce `event.key === 'x'`/`'X'`, or where `Shift+8` does not yield `'*'`: out of scope, no AC states layout independence.
- **Real focus rings, real OS-level auto-repeat timing/rate, a real browser's exact default-action semantics for every element type**: outside the stub by construction (RK-2, RK-3). The stub's native-activation simulation (item 11 above) is a deliberate, documented approximation for `<button>` only.
- **CSS, layout, dark theme, responsive layout, real `file://` loading**: unchanged scope from `BOOT-001`/`CALC-001`; `UNVERIFIED`, manual checklist stays with the user.
- **`CALC_STUB_TRANSFORM` gate-evidence gap** (carried-forward item 5): explicitly not a row here; forwarded to the orchestrator as a human (`run-gate.mjs`) decision.

## Mutation sanity (what each key behavior would miss without its row)

- Key map maps a numpad-specific literal (`"Numpad5"`) instead of relying on `event.key` normalization: nothing catches this directly (no such literal is ever dispatched by a real browser), but the digit-mapping row would still pass, which is correct — the note explains why no row is needed rather than pretending one exists.
- Key map forgets the `x`/`X` → `*` alias: "maps each operator key including the letter x and its capital…" fails.
- Key map lets `Ctrl`/`Meta`/`Alt` through: the modifier-blocking unit row and the two integration modifier rows fail; `Cmd+/` specifically catches a mapper that only checks `ctrlKey`.
- Key map blocks on `Shift`: the two Shift-does-not-block rows (unit and integration) fail.
- Repeat policy allows a held operator or `Enter` through: the two call-count-spy integration rows fail (the display-only rows would not catch this — documented).
- `dom-stub.js`'s native-activation simulation always fires regardless of `preventDefault()`: not directly probed by a row (no scenario in this matrix calls `preventDefault()` on a focused-button `Enter`/`Space`), but a broken listener that wrongly does so would show zero actions instead of one in the Tab-activation rows, which would fail them — an indirect but real catch.
- `script.js`'s click handler forgets to call `blur()`: "a mouse click blurs its button so a following Enter…" fails (`4+84` instead of `4+8`/`12`).
- The key listener does **not** ignore `Enter`/`Space` when `event.target` is a calculator button: the Tab-activation rows show two actions (`77` instead of `7`, or a call-count of 2 instead of 1) instead of one.
- The `data-operator`/`data-action` boundary filters are removed from `script.js`: the two carried-forward item-1 integration rows throw instead of silently ignoring.
- `stripComments` is left unfixed: the new regression row in `source-safety.test.js` stays RED (the literal `eval(` reference).
- The AC-7 scan is left un-widened to `index.html`: the three modified `source-safety.test.js` rows would not catch a probe injected into `index.html` (verified conceptually; not re-probed here since the fix is designed, not yet implemented).
