# KEY-001 — Keyboard input drives the calculator

## Objective
Typing on a physical keyboard operates the calculator exactly as clicking the on-screen
buttons does: digits and `.` enter numbers, `+ - * /` choose operators, `Enter`/`=` evaluates,
`Backspace` deletes, `Escape` clears — through the same dispatch path and the same state
machine, without double actions or stolen browser shortcuts.

## Context
Requirements R-01…R-08 and R-13 in `.agent/plan.md`. After BOOT-001 the state machine lives in
`calculator-core.js`, so the key map can be a pure function (`mapKey(key, modifiers)` →
input descriptor or `null`) that is unit-testable in Node, while `script.js` gains a single
`keydown` listener on `document` that feeds the shared `dispatch(input)` used by clicks.

`event.key` is used (not `event.code`) because it is layout- and numpad-normalized. Input
handling is a `security-reviewer` trigger (CLAUDE.md §8): the map is a closed allowlist, and
nothing input-derived may reach `innerHTML`, `eval` or `new Function`.

CALC-001 (the mid-chain divide-by-zero fix) is sequenced before this unit so that only one unit
at a time edits `calculator-core.js`; the key-vs-click parity tests below therefore assert the
**fixed** divide-by-zero behavior (`5 / 0 +` → expression `5÷0`, current `Error`).

The exact map and three behavioral details were **resolved** by the user on 2026-09-21 (OQ-1…
OQ-4 defaults accepted); the ACs below stand as written.

## Dependencies
- `BOOT-001` — provides the importable pure core, the shared dispatch seam and the

- `CALC-001` — fixes the mid-chain divide-by-zero defect in the same core file. Serialized

## Acceptance Criteria
(Assumes the OQ-1…OQ-4 defaults; a different answer changes the listed keys, not the shape.)
- AC-1: Given the loaded page, when the keys `4`, `+`, `8`, `+`, `9`, `Enter` are pressed
  (`keydown`), then the display shows expression `4+8+9` and current `21` — identical to the
  same sequence performed with clicks.
- AC-2: Given the loaded page, when `0`, `.`, `1`, `+`, `0`, `.`, `2`, `=` are pressed, then the
  current display is `0.3`; and when a second `.` is pressed inside the same number, then the
  display is unchanged (one decimal point per number).
- AC-3: Given the loaded page, when `*`, `x`, `X`, `/`, `-` and `+` are pressed as operator
  keys, then the expression trail shows the display symbols `×`, `×`, `×`, `÷`, `−`, `+`
  respectively (operator keys map to the same operators as the buttons).
- AC-4: Given the display shows `123`, when `Backspace` is pressed, then the display shows `12`;
  and given any state, when `Escape` is pressed, then the display shows `0` with an empty
  expression line (same as `AC`).
- AC-5: (scope carve-out recorded 2026-09-22, `.agent/decisions/D-013-native-activation-is-the-browser-channel.md`
  clause 4: `preventDefault()` also fires for a *repeat* `Space`/`Enter` whose target is a focused
  calculator button, to suppress repeat native activation per AC-6 — this governs keys that do not
  target a calculator button.) Given the loaded page, when an unmapped key (`a`, `F5`, `Tab`, `ArrowLeft`, `Space`) or
  any mapped key held with `Ctrl`, `Meta` or `Alt` (e.g. `Ctrl+R`, `Cmd+/`) is pressed, then the
  calculator state and both display lines are unchanged **and** `preventDefault()` was not
  called (the browser keeps its own behavior); whereas for a mapped, modifier-free key
  `preventDefault()` was called exactly once.
- AC-6: (superseded 2026-09-21, user decision, see OQ-3) Given a button was activated with a mouse
  click, when the click handler runs, then that button no longer has focus afterwards (a `blur()`
  call), so a subsequent `Enter` or `Space` press is read by the keyboard listener as a normal key,
  not as a repeat of that button — for example click `4`, type `+ 8`, press `Enter` renders `4+8`
  and `12`, not `4+84`. Given a button reached by `Tab` (not by a click) has focus, when `Enter` or
  `Space` is pressed and the browser natively activates that focused button, then exactly one
  calculator action occurs — the key handler ignores `Enter`/`Space` events whose target is a
  calculator button, so keyboard-only users keep standard button activation and never get two
  actions from one press.
- AC-7: Given a key is held so the browser emits auto-repeat events (`event.repeat === true`),
  when the key is a digit, `.` or `Backspace`, then each repeat performs its action; when the
  key is `Enter`, `=` or an operator, then repeats after the first are ignored (state unchanged).
- AC-8: Given `README.md`, when a user reads it, then it documents the complete key map
  (which key does what) and the keyboard support is listed under Features.

## Required Tests

  `Escape`, `Delete`); unmapped keys (`a`, `F5`, `Tab`, `ArrowLeft`, `Space`, `Shift`, `` ` ``)

## Risks / Open Questions
- **OQ-1 — RESOLVED 2026-09-21 (user accepted the default)**: map = digits + numpad, `.`, `,`,
  `+ - * /`, `x`/`X` → ×, `Enter` and `=` → equals, `Backspace` → DEL, `Escape` and `Delete` → AC.
  Not mapped: `:`, `c`/`C`.
- **OQ-2 — RESOLVED (default)**: `preventDefault()` only for mapped keys with no Ctrl/Meta/Alt
  held; never for `Tab`.
- **OQ-3 — RESOLVED 2026-09-21 (user overrode the proposed default)**: the proposed default (keep
  native activation, handler ignores `Enter`/`Space` on a focused calculator button) had a defect
  the user caught: a mouse click leaves the clicked button focused, so `Enter` afterwards would
  replay that button's click instead of computing (`4`, `+`, `8`, `Enter` would type another `4`
  instead of evaluating). **Resolution: a mouse click blurs its button afterwards** (`element.
  blur()` in the click handler, mouse-initiated clicks only — a `Tab`-then-`Enter`/`Space`
  activation is unaffected and keeps native behavior). AC-6 rewritten accordingly. `Space` is
  otherwise unmapped.
- **OQ-4 — RESOLVED (default)**: repeat allowed for digits, `.`, `,` and `Backspace`; repeated
  `Enter`/`=` and repeated operators are ignored.
- RK-2 (owner: implementer): stub fidelity is the main threat to AC-5/AC-6/AC-7 being meaningful.
- RK-5 (owner: security-reviewer): over-broad `preventDefault()` breaking browser shortcuts or
  `Tab` navigation.
- RK-3 (owner: user): no real browser — real keyboard behavior needs a manual pass. Manual checklist
  (accumulated across cycles, see `.agent/decisions/D-011`, `D-013`, reviews `r2`, `r3`):
  1. mouse-click a button, then type more keys — expect no repeat of that button's value (r2 F-3).
  2. touch-tap a button on a touch device, then type/tap likewise — expect the same (r2 F-3).
  3. Tab to a digit button, hold `Enter` — expect the digit exactly once, not repeated (r3 F-4).
  4. Tab to a digit button, hold `Space` — expect the digit exactly once, **not zero times** (real
     browsers activate a button on `Space` keyup, not keydown, which this fix's stub cannot model;
     r3 F-4, `D-013`'s residual risk).
  5. repeat check 3 on the `=` button (r3 F-4).
- RK-13 (owner: orchestrator): this unit's divide-by-zero parity expectations depend on CALC-001
  landing first; if CALC-001 is blocked or its OQ-C1 answer differs, re-read AC/test expectations
  here before this unit leaves `PLANNED`.

  AC-6 row sends one non-repeat keydown to a focused button; every AC-7 held-key row targets

  the cycle-2 code review reproduced this on a held-Enter-on-a-focused-**digit**-button case

  review's proposed decision (`D-012`) argued this was an inert residual, but its own examples
  (`=`, an operator swap) are idempotent and its proposed fix (`!allowsRepeat(input)`) would not
  have suppressed the digit case either (digits are deliberately repeatable under OQ-4). `D-012` was
  rejected by the orchestrator on this factual gap; see the record for the corrected reasoning.
  Fixed: repeat native button activation is now unconditionally suppressed regardless of input
  type, not gated by `allowsRepeat`.
